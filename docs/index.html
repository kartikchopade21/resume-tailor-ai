01

Problem & constraints

Rewrite a resume so an applicant tracking system scores it above 90% against a specific job description — without inventing experience the candidate doesn't have.

Two constraints shaped every decision that follows.

There is no free ATS scoring API

Jobscan, Resume Worded, Enhancv, LiveCareer and Resume.io are all web applications behind logins and paywalls. None publishes a scoring endpoint. Scraping them would break on the next markup change and violates their terms.

This turned out to be a fortunate constraint rather than a limitation. A black-box score from a website is a single number — it cannot tell the rewriter which keyword in which section cost points. A loop needs a gradient, not a verdict. So the scorer is reimplemented locally from the rubric those tools describe publicly, which makes it free, offline, unlimited, byte-identical across runs, and — critically — introspectable by the component that has to act on it.

The 90% target can be dishonest

Any resume can reach any score by stuffing keywords. The interesting engineering problem is reaching the target only through claims the candidate could defend in an interview, and reporting failure when that isn't possible. This constraint is enforced in three places: the router can decline to place a skill, the rewrite prompts forbid invented facts, and every generated line is tagged with provenance and surfaced for review before download.

02

Goals and non-goals

GoalHow it is met
Deterministic scoring No model call in the scoring path. The same resume and JD always produce the same number, so score changes are attributable to rewrites alone.
Steerable feedback Every score component exposes its own gap list; the loop feeds the whole report back into the next rewrite as text.
Surgical edits The resume is carried as structured JSON, not text, so one project can be rewritten without disturbing the rest of the document.
Honest failure The loop tracks the best version, detects plateaus, and reports blocking gaps by name instead of padding to hit the number.
Provider independence One protocol branch (Anthropic vs OpenAI-compatible) covers six providers, four of them free.

Explicit non-goals

  • Not a true ATS emulator. Real systems (Workday, Greenhouse, Taleo) each parse differently and none publish their algorithm. The scorer models the published rubric, not any specific vendor.
  • Not an autopilot. Generated bullets are claims about a person's history. The review panel is a required step, not a courtesy.
  • Not a resume builder. It transforms an existing resume; it does not author one from a blank page.

04

Data model

The single most consequential design decision is that the resume travels as structured JSON, not text. Text would force every rewrite to regenerate the whole document, which loses formatting, drops content silently, and makes it impossible to say what changed. 

ResumeDoc
├── contact      Contact(name, email, phone, location, linkedin, github, headline)
├── summary      str
├── skills       dict[category → list[str]]
├── experience   list[Experience(id, company, title, dates, bullets)]
├── projects     list[Project(id, name, subtitle, tech[], bullets, link)]
├── education    list[Education]
├── certifications, extras
└── raw_text     original extraction, used for parseability checks

Bullet
├── text    str
├── origin  "original" | "rewritten" | "added"   ← provenance
└── skills  list[str]                            ← which JD skill it demonstrates

Stable id fields (proj1, exp2) are what make surgical edits possible: the router returns an id, the rewriter returns a patch keyed by that id, and _apply_patch merges it into a copy while leaving every other entry byte-identical.

The origin field on every bullet is the honesty mechanism made structural. It survives the whole pipeline, drives the review panel, and lets added_claims() enumerate exactly what the system wrote on the candidate's behalf.

Invariant

The patch applier never drops a pre-existing skill. Any skill in the original that the model omits from its returned skills map is re-appended under Additional Skills. A rewrite can add to the candidate's record; it cannot silently delete from it.

05

The control loop

This is the mechanism the whole system exists to run. Each round converts the previous score's gap report into targeted rewrites, then re-scores. The loop is a hill climb where the score function is deterministic and the step function is a language model.

Termination

Three conditions end the loop, and the distinction between them is what the user is told afterwards:

  • Target met — the score reached the threshold. Stop immediately; further rounds can only add unnecessary claims.
  • Plateau — from round two onward, an improvement below 1.0 points means the remaining gaps need real experience, not rewording. Stopping here is a finding, not a failure.
  • Rounds exhausted — five rounds without convergence, which in practice means the JD and the resume are a poor match.
Subtlety worth knowing

Round zero scores the uploaded file, including its format penalties — tables, text boxes, multi-column layout. Every subsequent round scores against a synthetic clean audit, because the delivered artifact is the pipeline's own single-column DOCX, not the original file. Without this, a resume would be permanently penalised for formatting the pipeline is about to fix.

Scoring subsystem

Six weighted components summing to 100. Each one contributes its own section to the gap report, which is what the rewriter consumes.

ComponentWeightMeasuresGradient source
Hard skills40Required skills ×2, preferred ×1, weighted by where each appearsPer-skill credit
Keyword coverage20Verbatim JD keyword surface forms found anywhereMatched / total
Parseability15Tables, images, text boxes, columns, header content, fonts, lengthPer-issue penalty
Title match10Target job title in headline, summary or a role titleToken-set ratio
Completeness10Email, phone, location, links, summary, education, skillsWeighted checklist
Responsibilities5Token overlap between JD duties and bullet textPartial credit

Location weighting

The design decision that gives the three rewrite scopes genuinely different ceilings: the same keyword is worth different amounts depending on where it sits. A skill listed but never demonstrated earns 70% credit; the same skill inside a project bullet earns full credit.

Matching

Naive string matching fails immediately: a JD says LLMs, a resume says LLM-powered, and a substring test misses it. Four layers handle this, cheapest first:

  1. Normalisation — lowercase, punctuation stripped, whitespace collapsed.
  2. Joiner splitting — llm-based → llm based, ci/cd → ci cd. Both forms are indexed, so a keyword glued to a suffix is still found.
  3. Alias groups — 36 bidirectional sets: LLM ↔ large language model, k8s ↔ Kubernetes, scikit-learn ↔ sklearn, plus automatic plural and singular variants.
  4. Fuzzy fallback — n-gram comparison at 88% similarity, length-gated to avoid short-token false positives.

Responsibility matching adds crude suffix stemming (pipeline / pipelines / pipelining collapse) and awards partial credit rather than using a threshold. A binary cliff there starved the loop of signal — an early version scored 1.0 out of 5 on a resume that clearly addressed four of the five duties, because no candidate ever echoes a JD's phrasing word for word.

07

Skill routing

The distinctive component. When the JD demands a skill the resume never mentions, something has to decide where that skill plausibly belongs — and that decision is judged by technical adjacency, not by keyword similarity or project size.

Routing is a separate model call from rewriting, for three reasons: the decision is auditable on its own, its rationale can be surfaced in the UI, and it produces a structured refusal path that a combined write-it-all-at-once prompt would quietly skip.

Three rewrite scopes

Dropdown optionTouchesSample ceiling
Add in skills onlySkills section80.7%
Add it in projects and skillsRouted projects and roles, then the skills section89.6%
Add overall in the resumeHeadline, summary, skills, all projects and experiencehighest

The ceilings are not arbitrary — they fall directly out of the location weighting in §6. Skills-only mode cannot exceed 70% credit on any skill it adds, because it has nowhere to demonstrate them.

08

Provider abstraction

Six providers, two protocols, one branch. Everything except Anthropic speaks the OpenAI chat-completions format, so adding a provider is a registry entry: base URL, key source, default model, output token cap.

Making open models emit strict JSON

This is where most of llm.py's complexity lives. Frontier models return clean JSON on request; smaller open-weight models return fenced blocks, chatty preambles, and <think> reasoning traces. Four defences, applied in order:

  • Native JSON mode via response_format, with automatic fallback for gateways that reject it.
  • Reasoning-block stripping and code-fence extraction.
  • Brace-matched scanning that respects string escapes, so a JSON object embedded in prose is still recovered.
  • An explicit repair round trip — the malformed reply is named as such and the temperature is lowered.

Performance & cost

Model calls follow 2 + 2n where n is the number of rewrite rounds: one parse, one JD extraction, then a routing call and an apply call per round. A typical two-round run is six calls — confirmed against an instrumented endpoint.

StageCallsDominant cost
Parse resume1Input ≈ full resume; output ≈ structured JSON
Parse JD1Input ≈ full JD; output ≈ 4k tokens
Route skills1 / roundInput ≈ project inventory; output small
Apply rewrites1 / roundLargest call — up to 8k output tokens
Score0Pure local computation, sub-millisecond
Render0LibreOffice subprocess, ~2s for the PDF

Groq's free tier allows roughly 30 requests per minute and 1,000 per day, so the daily cap is irrelevant at six calls per run — the per-minute token budget is the real constraint on back-to-back runs, which is why Groq's output cap is set to 4,000 tokens rather than 8,000. Ollama has no quota at all, trading throughput for independence.

11

Security & privacy

A resume is a dense package of personal data — full name, phone number, home city, employment history. Two decisions follow from that.

  • Keys are never persisted by the application. A key typed into the sidebar lives in memory for that session only. Persisted keys go in .env, which is gitignored; the repository ships only .env.example with placeholders.
  • Resume content reaches whichever provider is selected. This is unavoidable for a hosted model and worth stating plainly. The Ollama path exists precisely for people who would rather it didn't — it runs on localhost, and nothing leaves the machine.

Nothing is logged to disk, no telemetry is emitted, and uploads are written to a temporary file that is deleted in a finally block after parsing.

12

Limitations

Stated directly, because a design document that only lists strengths isn't one.

  • The score models a published rubric, not a specific vendor. Workday and Greenhouse parse differently from each other, and neither publishes its algorithm. A 90 here is a strong signal, not a guarantee about any one employer's stack.
  • Routing quality tracks model capability. A 14B local model is noticeably weaker at the adjacency judgement than a 70B one. If routing looks careless on Ollama, that is the model, not the logic.
  • The honesty constraints are prompt-enforced, not provable. The patch applier can guarantee that no skill is dropped and that provenance is recorded; it cannot verify that a rewritten bullet is true. That is what the review panel is for, and why it is not skippable.
  • Single-pass parsing. An unusual resume layout — heavy tables, a two-column CV — parses into a structure the pipeline then treats as ground truth. Format audit warns about this; it does not repair it.

Extension points

  • New provider — one entry in the PROVIDERS registry, no other code.
  • New scoring component — add a field to Weights, a computation in score_resume, and a line in gap_summary; the loop picks up the new gradient automatically.
  • New alias group — one list appended to ALIAS_GROUPS.
  • New output format — a writer function in render.py; the document model is already format-agnostic.
